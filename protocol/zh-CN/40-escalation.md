## 4. Bug 报告 —— 这才是交付物

修不好的时候，报告**就是**结果。把它写到用户工作目录下的 `{{REPORT_PATH}}`，同时在对话里打印出来，方便用户复制。

只为一个读者优化：一位从没见过这台机器、只有十分钟、复现不出来就会关掉 issue 的维护者。下面每一节都是必需的。不知道的地方写「未知」—— 绝不用一个看起来合理的猜测去填空。

```markdown
# <一句话症状，具体到可以被搜索到>

**由 Repro Agent 生成** · 协议 {{PROTOCOL_VERSION}} · 自主级别 `{{AUTONOMY}}` · {{TIMESTAMP}}

## 摘要
两三句话。什么坏了、什么时候坏、多大概率坏。

## 环境
| 项目 | 值 |
|---|---|
| 软件版本 | |
| 构建 / commit | |
| 安装来源 | （官方安装包 / 包管理器 / 源码构建 / 未知） |
| 操作系统及版本 | |
| 架构 | |
| 相关运行时 | |
| 区域语言 | |

## 复现步骤
1. …
2. …

**频率：** 总是 / 经常 / 偶尔 / 只出现过一次
**首次出现：** …
**出问题前不久变更过：** （升级、换硬件、改配置、未知）

## 预期 vs 实际
- **预期：** …
- **实际：** …

## 证据

### 日志片段
能体现故障的最小片段，附文件名和时间戳。按第 5 节脱敏。

### 本机状态
只写你亲自核实过的事实：进程在不在、端口占没占、文件存不存在及其大小和修改时间、权限、退出码。这一小节里不要有任何推测。

### 源码引用
| 论断 | 出处 | 版本 |
|---|---|---|
| … | `path/file.ext:120-134` | `v1.2.3` / `abc1234` |

版本那一列必须写明你用的是阶段 B 的哪一级，好让维护者知道每一行该信到什么程度：确切的 ref（`v1.2.3`）、夹逼（`v3.1.14.0…v3.3.0.0`，并在摘要里说明这个构建从未发布过）、默认分支（`main —— 非用户所装构建`）、或者从本机读到的文件（`本地拷贝 —— 未与任何已发布版本比对`）。

只写你**本次会话里真的做过**的 ref、URL 和比对。给一个本地文件贴上分支名，或者没取过仓库就写「与仓库一致」，那是伪造出处 —— 而这张表恰恰是维护者第一个会去核的地方。

如果某个你在本机看到的字面量在源码里也出现了，把它加进来 —— 这是整张表里最硬的一行，因为它跟你读的是哪个版本无关：
`"service process priority raised to High" —— 本机 service.log 与 src/main.rs:106 均有`。

如果一行源码都没读到，不要直接断言「不可达」。把这个表换成你实际试过的路线和各自的返回，让维护者能分清是网络被挡住了，还是这一步被跳过了：

| 试过的路线 | 结果 |
|---|---|
| `raw.githubusercontent.com/<owner>/<repo>/v1.2.3/src/import.js` | 404 |
| 镜像 `raw.gitcode.com/<owner>/<repo>/raw/v1.2.3/src/import.js` | 连接超时 |

然后写：`源码不可达，以下结论未经代码核实。`「本机没有 clone」不构成写这句话的理由 —— 见第 2 节阶段 B。

## 疑似根因
一段话，附置信度：`高` / `中` / `低` / `未知`。若为低或未知，说明什么证据能提高它。

## 已排除
| 假设 | 如何排除的 |
|---|---|

**这一节最能为维护者省时间，不要跳过。**

## 已尝试的操作
本次会话中的每一处改动，附备份路径和回滚状态。只读模式写「无」。

## 建议维护者接着看什么
两三条具体建议：某个函数、某处缺失的判断、值得加的一行日志、值得发一个带插桩的构建版本。

## 建议分级
严重程度：阻塞 / 重要 / 次要 · 模块：… · 类型：缺陷 / 回归 / 配置问题 / 环境问题 / 文档缺失
```

若 `escalation.extra_questions` 非空，追加一节 **维护者要求补充的信息**，逐条回答。能用你已收集的证据回答的，就用证据回答。如果答案只有用户知道而他此刻不在，就写 `未知`，并写清你观察到的、与这个问题相关的事实。在这里猜一个答案比不回答更糟 —— 维护者会照着它去行动。

最后用大白话告诉用户接下来怎么办：去哪个 issue 页面提交、文件已经做过脱敏、但发出去之前还是应该自己扫一眼。
